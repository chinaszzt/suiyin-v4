# SDD 方法论 — 项目协作对齐

> 本文档定义碎银 v4 项目怎么用 **Spec-Driven Development（SDD）** 协作。所有参与者必须在方法论上对齐——SDD 不是给个别人看的流程，是整个项目的工程契约。新人加入第一周必读。

---

## 30 秒版：5 条协作铁律

如果你只能记 5 条，记这 5 条。剩下章节是它们的依据和实操。

1. **任何新能力先写 spec 再写代码**——不能跳。
2. **Spec 只写"用户/外部观察者可观察的行为"**——含异常、边界、外部约束传染。
3. **Bug 第一步翻 spec**——按 A/B/C/D 分类处理，找不到 spec 不能绕过。
4. **改代码必须同步改 spec**——一个 PR 解决，spec rot 的死敌。
5. **拍板前移到 spec / plan 阶段**——抠 PR diff 是浪费资深判断力。

---

## 〇、一句话定义

**Spec-Driven Development**：把"要做什么 / 为什么"用人和 AI 都能读的文字钉死，作为代码的**唯一真实来源**。AI 在受控的 spec 下实现，人在 spec 阶段拍板。**代码是 spec 的产物，不是反过来**。

---

## 一、为什么我们要用 SDD

LLM 编程时代之前，"需求文档 + 设计文档"很少有人爱写——因为人写代码不严格依赖它，团队靠走廊对话和默契补齐。

但 LLM 上下文有限、容易自由发挥、跨 session 失忆。**Spec 变成了 AI 编程的"持久内存"**：

- 每次拉起 AI 都能把 spec 当 anchor 塞回去，意图不漂移。
- 多 session 接力时，spec 是唯一可靠的传承介质（聊天记录会丢、memory 是松散的）。
- 防止 AI"自由发挥"偏离意图——它必须照 spec 实现，不照就在 review 阶段被拦截。

2025 年关键节点：GitHub 开源了 [spec-kit](https://github.com/github/spec-kit)，AWS 出了 Kiro IDE，主流 AI 编辑器都加了 spec mode。SDD 从工程师内部博客变成有 cli + slash command 的成熟工具链。

我们用 SDD 不是赶时髦，是因为 v4 是"AI 主力实现 + 人拍板 + 多 session 接力"的项目，spec 对我们而言**就是 AI 的长期记忆**。

---

## 二、3 条核心理念

| 理念 | 含义 | 跟传统开发的差 |
|---|---|---|
| **意图与实现分离** | spec 描述"行为契约"，不写 widget / SQL / 接口具体协议；实现可以重做，但行为不变 | 传统设计文档常常一上来就画类图 |
| **可验证规范** | spec 里每条"用户能做 X"都对应一条**可执行的验收标准**（测试 / 演示步骤） | 传统需求文档常常是"提升体验"这种没法验证的话 |
| **拍板前移** | 决策点从"PR review"前移到"spec / plan review"。改 spec 比改代码便宜 100 倍 | 传统流程是写完再改，反复返工 |

## 三、工作流 5 阶段

每个阶段都是**一份文件 + 一次人审**。文件路径见仓库 `docs/sdd/` 目录约定。

### 3.1 Constitution（项目宪法）

- 写一次，偶尔追加。**所有 spec 受它约束**。
- 路径：`docs/sdd/constitution.md`
- 内容：技术栈、目录结构、错误约定、测试边界、提交 / PR 规约、审美。
- 评审重点：会不会把团队锁死？有没有"该硬性约束的"被遗漏？

### 3.2 Specify（单个能力的 spec）

- 一个能力一份文件：`docs/sdd/specs/NNN-feature-name/spec.md`
- 内容：用户故事 + 屏幕/接口外部行为 + 验收标准 + **不在范围**。
- **禁止写实现细节**。看到 widget / 路由 / 数据库结构立刻挪走。
- 评审重点：是否完备覆盖正常 + 异常 + 边界？每条验收标准是否**可证伪**？

### 3.3 Clarify（澄清轮）

- AI 反过来问你："这块我不确定是 A 还是 B"。把模糊点钉死。
- 不做 clarify，AI 后面就**自己猜**——猜错的概率非常高。
- 评审重点：所有"AI 必须自己做决定但 spec 没写"的点是否都被回答？

### 3.4 Plan（技术方案）

- 路径：`docs/sdd/specs/NNN-feature-name/plan.md`
- 内容：架构、数据模型、依赖、并发 / 重试策略、关键风险。
- 这一步才允许谈实现。
- 评审重点：选型是否符合 Constitution？跨域接口是否清晰？关键风险是否有应对？

### 3.5 Tasks → Implement

- 路径：`docs/sdd/specs/NNN-feature-name/tasks.md`
- 拆成可独立 PR 的小任务清单，每条挂 spec / plan 锚点（行号或 anchor）。
- 执行：每个 task 开 worktree，按 spec / plan 实现。
- 审 PR 时**只对照 spec 验收标准**，不抠代码细节（Constitution 已定调）。

注意 **3.3 → 3.2 是会回头的**：clarify 触发 spec 修订是常态，不是失败信号。

## 四、Spec 怎么写：颗粒度与边界

### 4.1 颗粒度

**横向（一个 spec 多宽）**：spec 是"用户能完成的一件有意义的事"——**端到端的能力切片**，不是按代码模块切。

- ❌ "客户档案数据模型"——这是实现切片，不是用户能完成的事
- ❌ "整个客户管理系统"——太大，没法独立验收
- ✅ "销售可以在列表里筛选当前分给自己的客户"——端到端、可演示、可验收

**纵向（一个 spec 多深）**：写到**"足够让另一个工程师 / AI 实现出可被你接受的版本"为止**。多一句都是过度规约。

- ✅ "列表按最近联系时间倒序"——合理 spec
- ❌ "列表第一列宽 120px、字体 14sp"——细节，归 design 阶段

### 4.2 写什么：用户 / 外部观察者可观察的行为

**Spec = 系统对外可观察行为的完整契约。**

"外部观察者"按 spec 类型不同：

- 前端 spec → 终端用户
- 后端 API spec → 调用方（前端、其他服务）
- 数据管道 spec → 下游消费者
- 运维相关 spec → 告警 / 监控接收人

**判定锚点**：有没有外部观察者会因为这个行为做不同的事？没有 → 是实现细节，不进 spec。

### 4.3 异常和边界必须写

异常和边界**必须**进 spec，因为用户感知得到。不写 = 漏验收点 = Type B bug 的种子。

- "密码错 5 次冻结 15 分钟"——是 spec
- "网络断时显示离线提示并把消息排队"——是 spec
- "重试 3 次失败后弹错误对话框"——是 spec

### 4.4 外部强约束："传染"才进 spec

外部约束只在它**传染**成用户可观察行为时才进 spec。

| 约束 | 用户可观察？ | 归属 |
|---|---|---|
| E云"同 wcId 不能并发 + 250ms 间隔" | ✅ 消息排队、UI 提示 | spec |
| 合规要求日志保留 90 天 | ❌ 用户感知不到 | constitution / plan |
| 数据库连接池上限 100 | ❌（除非超出导致服务挂） | plan |
| GDPR"用户可申请删除自己的数据" | ✅ 有"删除账户"按钮 | spec |

**判定标准依然是可观察性，不是"外部约束"这个标签本身。**

### 4.5 设计图怎么对应

设计图横跨多层，**不能整体归类**。要拆开看它在描述什么：

| 设计图描述的东西 | 归属 |
|---|---|
| 用户能看到什么信息 / 能做什么操作 | spec |
| 信息层次、布局结构（线框图层级） | spec 或 design |
| 视觉风格：颜色、字体、间距、动画 | design（不进 spec） |
| 具体组件选择 | 实现 |

**实战处理**：Figma 链接作为 spec 的附件。判定它变了 spec 改不改的锚点还是"用户可观察行为有没有变"。换皮肤 → spec 不动。加交互 → spec 同步加。

## 五、Clarify 阶段的反直觉哲学

**普通直觉**：我先把 spec 写到面面俱到，AI 就不用问了。

**SDD 反直觉做法**：先写一个不完整的 spec，然后让 AI 反过来扫一遍，**列出"我要实现这个 spec，但有以下 N 个地方我没法决定 / 可能会自己猜"**。你回答这些问题就是 clarify，答案直接写回 spec。

为什么反过来更有效：

1. **人不知道自己漏了啥**。你写 spec 时大脑会自动跳过"显然"的地方。AI 没有"显然"——它必须为每个分支做决定。
2. **暴露的是"决策"不是"知识"**。AI 不会问"什么是登录"，会问"两次输错密码后是冻结、提示、还是无操作"——这些都是要**人拍板**的事，不是 AI 能查到的事。
3. **Clarify 是拍板前移的载体**。每个 clarify question 都是一次小拍板，决策粒度从"接受一个 PR"变成"回答 10 个二选一"，决策成本指数下降。

**实战姿势**：spec 草稿写完，丢给 AI："假装你要实现这份 spec，列出你必须自己做决定但我没写的所有地方，按影响范围排序"。它列 15 条，你逐条回答。这一轮做完，spec 才算成熟。

## 六、拍板的 4 个层次

"我拍板"实际上是 4 个不同层级，每层关心的事和翻车成本天差地别：

| 层级 | 拍什么 | 翻车成本 | 频次 |
|---|---|---|---|
| **Constitution** | 技术栈、目录、错误约定、测试边界、审美 | 极高（推翻 = 重构整个项目） | 一次性 + ADR 追加 |
| **Spec** | 这个能力做什么 / 不做什么 / 验收标准 | 高（推翻 = 丢掉所有下游产物） | 每能力一次 |
| **Plan** | 这个能力怎么做：架构选型、数据模型 | 中（推翻 = 重写 task，spec 还在） | 每能力一次 |
| **PR** | 代码细节、命名、风格 | 低（推翻 = 改几行） | 多次 |

**关键洞察**：传统模式拍板主要在 PR 层——看跑出来的代码 OK 不 OK。SDD 把注意力**向上拉**。同样 1 小时审 spec 顶过审 10 个 PR，因为你在更高杠杆点上做决定。

**实战姿势**：

- **Constitution**：亲自定调，AI 起草，你逐条过。
- **Spec**：审"用户故事 + 验收标准 + 不在范围"，实现细节扫两眼就过，看到立刻让 AI 移走。
- **Plan**：审"架构 + 跨域接口 + 关键风险"，不审代码。
- **PR**：只对照 spec 验收标准看跑出来对不对，不抠代码风格。

**抠 PR diff 是浪费资深判断力**——Constitution 已经定了风格，PR 层不该是决策点。

## 七、Bug 处理流程

### 7.1 强制工作流：先翻 spec

每个 bug 第一步都是**找到相关 spec → 对照验收标准逐条检查**。这是 SDD 让 spec 保持鲜活的最高频触发点。

```
bug 报告
  ↓
找到相关 spec（流程强制第一步）
  ↓
对照验收标准逐条检查
  ├─ AC 覆盖了 + 实现错      → Type A：改代码 + 加回归测试
  ├─ AC 没覆盖到            → Type B：补 AC → 改代码 + 回归测试
  ├─ AC 有但写错了/产品意图变 → Type C：改 AC + 写 ADR → 改代码
  └─ AC 覆盖了 + 实现对了 + 还是 bug
                          → spec 违反外部物理事实，升级讨论
```

**找不到相关 spec 怎么办？** 两种可能：

- 这能力还没 SDD 化（标记为遗留代码）
- 这个 bug 揭示了 spec 体系有盲区（开 task 补 spec）

**两种都不能"那就直接改代码吧"绕过。**

### 7.2 4 种 Bug Type

#### Type A：实现偏离 spec（最常见）

- **场景**：spec 说"密码错显示提示"，实现成"刷新整页"。
- **处理**：改代码 + 加回归测试，spec 不动。
- **注意**：如果你想标 A 但发现 AC 模糊到能解释成 bug 行为——其实是 Type B 伪装的 A，去补 AC。

**AC 是否可证伪的测试**：两个人独立读这条 AC，能不能写出同一个测试用例？能 → 可证伪。不能 → 改写 AC。

#### Type B：spec 没覆盖的边界（最容易引发 spec rot）

- **场景**：spec 没说"连错 N 次怎样"，实现成无限重试，被爆破。
- **处理**：**先补 spec**（加"5 次冻结 15 分钟"+ AC）→ 再改代码。
- **只改代码不补 spec = 埋下 rot 种子**。下次新人读 spec 会以为这是实现细节，可能改掉。

#### Type C：spec 本身错了（最危险）

- **场景**：spec 说"按发送时间排序"，用户反馈说"我们要的是接收时间"。
- **处理**：**先改 spec + 写 ADR**（记录"为什么从 X 改成 Y、用户反馈是啥"）→ 再改代码。
- **必须留 ADR**——否则三个月后这个反直觉的设计会被下一个 PR 改回去。

**降低 Type C 频率的机制**（不靠"找好产品经理"）：

- **Clarify 是过滤器**：很多 Type C 在 spec 阶段就被拦截。
- **早期可验证演示**：spec 写完做 mock / 静态 demo 给真实用户看，比上线后再发现错强 100 倍。
- **ADR 累积复利**：三年后翻 ADR 会发现"我们这类需求总猜错"的规律，下次警觉。

#### Type D：紧急 P0

- **场景**：生产挂、数据丢、安全洞。
- **处理**：先 hotfix 止血 → **24 小时内必须补 spec PR**。
- **超时阻断下一个发布**是工程化兜底，不允许"等下次再补"。

### 7.3 工程化硬约束（不靠自律）

1. **Bug ticket 模板第一项 = "相关 spec 路径"**，不填不能提交。
2. **PR 模板要求标 type + 链 spec 改动**。Type B / C 的 PR 必须含 spec 改动，CI 校验。
3. **代码挂 spec 锚点**：关键函数顶上 `// spec: docs/sdd/specs/042-login/spec.md#session-timeout`。CI 校验路径存在。
4. **Hotfix 自动开"24h 补 spec"issue**，超时阻断下一个发布。

## 八、Spec rot 防御

**SDD 最大失败模式 = 代码漂走但 spec 没更新。** 半年后 spec 变成考古文献，比没 spec 还糟——AI 会照着错 spec 实现。

防御 4 条：

1. **改代码必须改 spec**（写进 Constitution，PR 模板设 checklist）。
2. **代码挂 spec 锚点**（同 7.3 第 3 条）。代码改了搜索就能找到对应 spec。
3. **每个 bug 都是 spec 体检**（同 7.1 工作流）——这是最高频的鲜活机制。
4. **季度 spec 对账**：AI 拉一遍所有 spec 跟当前代码对比，列出漂移点。这是**兜底**，正常流程不该依赖它。

## 九、SDD 不适用的场合（反向定义）

SDD 原教旨主义会让你写 spec 写到崩溃。哪些事**不**走 SDD：

| 场合 | 怎么处理 |
|---|---|
| **探索性 spike** | 先 spike 拿到结论再写 spec，不要凭空 spec 一个未知数 |
| **纯 bug fix（Type A）** | 直接修代码 + 加回归测试，不开新 spec |
| **数据修复 / 一次性脚本** | 写个 README + 脚本就够，不进 spec 体系 |
| **明显的微小改动** | 文案、间距、日志——挂在最近相关 spec 下补一行 changelog 就够 |
| **被外部完全约束的事** | 接入第三方协议照抄文档，没拍板空间不需要 spec |

**判定法**：问自己"这事我有没有拍板空间？拍板错了代价大不大？" 两个都是 yes 才走 SDD。两个都 no 就直接干。

## 附录 A：术语对照表（SDD vs 敏捷 / 传统）

| SDD 术语 | 大白话 | 跟敏捷 user story 的关系 |
|---|---|---|
| **Spec** | 一个能力的行为契约文档 | 包含 user story，但更完备（含异常 / 不在范围 / 外部约束 / 跨 spec 关联）。是"对话结果"不是"对话开始" |
| **Acceptance Criteria (AC)** | 验收标准 | 跟敏捷 AC 一样，但 SDD 要求每条**可证伪** |
| **Constitution** | 项目宪法 | 接近敏捷的 Team Charter + Engineering Standards |
| **Clarify** | AI 反问澄清 | 敏捷里靠走廊对话补齐的部分，SDD 把它结构化进流程 |
| **Plan** | 技术方案 | 接近敏捷的 Technical Design |
| **ADR** | Architecture Decision Record | 决策记录文档，标注"为什么从 X 改成 Y" |
| **Spec rot** | spec 跟代码不同步 | 敏捷里的"文档过期"问题，但 SDD 后果更严重——AI 会照着错 spec 实现 |

**Spec 不是更详细的 user story。** 核心区别不是详细程度，是**承载者从团队变成文档**：敏捷假设有活的团队承载隐式知识，SDD 假设承载者是 AI session（没有团队记忆），所以原本团队共识里的东西必须文字化进 spec。

## 附录 B：Q&A 边界 case

讨论过程中暴露的典型边界，记下来给后来人。

**Q：spec 改是不是项目失败信号？**
A：不是。Clarify 触发 spec 修订是常态。Type C bug 触发 spec 修订也是常态。**改 spec 是好事，关键是改完留痕（ADR）**。

**Q：所有项目都该用 SDD？**
A：不。SDD 适用于"AI 主力实现 + 人拍板"+"多 session 接力"+"需求有拍板空间"的项目。爬虫脚本、数据修复、纯第三方协议接入不用。

**Q：拍板权能授权给 AI 吗？**
A：spec 和 plan 层**不能**——这两层是人的杠杆点。PR 层可以——Constitution 定调后，AI 自己能判断风格 OK 不 OK。

**Q：Type A 是不是说明 AC 写得不好？**
A：部分是。AC 写得好不能消除所有 Type A（代码总会有 bug），但能让 A 和 B 不会混淆——每个 bug 都能精准归类，处理路径不出错。如果你想标 A 时发现 AC 模糊到能解释成 bug 行为，那其实是 B 伪装的 A，去补 AC。

**Q：设计图变了 spec 就要改吗？**
A：看变的是行为还是皮肤。换皮肤 → spec 不动。加交互（如长按弹菜单）→ spec 必须同步。

**Q：写 spec 这么费劲，AI 不就是来加速开发的吗，是不是负优化？**
A：spec 不是负担，是把"调试 AI 写错的代码"的时间挪到"提前钉死意图"。总时间通常更短，且**质量曲线更稳**——AI 不会偏离，跨 session 不会失忆。短期看费劲，跑 3 个 feature 之后能明显感到收益。
